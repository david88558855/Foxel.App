Windows 系统托盘常驻方案

目标：Foxel 在 Windows 上以「托盘常驻程序」形态运行 —— 启动即隐藏、关闭只收进托盘、只有托盘菜单的「退出」才真正结束进程。 本稿只做方案，不改动仓库任何代码。

仓库 david88558855/Foxel.App 分支基线 v1.0.5+5 技术栈 Flutter 3.47.5 / Dart 3.11 · Win32 runner Dart 层改动 0 处 新增 pub 依赖 0 个
需求还原 方案选型 架构图 状态机 托盘菜单界面 改动清单 实现要点 / 坑 验收清单 远程编译 待你确认

1需求还原与验收口径

把你描述的三句话，翻译成可判定的行为定义 —— 有歧义的地方我按最严格口径落地。

你的原话行为定义（本方案口径）判定方式
程序启动后必定以最小化到托盘的模式运行 双击 exe → 进程起来、托盘出现图标、主窗口一次都不出现（不是"先闪一下再隐藏"）、任务栏无程序按钮 任务管理器有进程 + 任务栏无按钮 + 全程无窗口闪现
托盘图标右键弹出菜单，仅含「显示主窗口」「退出」 右键 → 光标处弹出系统原生菜单，只有 2 条：无分隔线、无图标、无"关于"、无"设置"、无三级子菜单 目视计数 = 2
关闭主界面 → 变成小托盘 点窗口右上角 X、按 Alt+F4、任务栏右键"关闭窗口" → 全部只隐藏、进程存活、托盘图标保留、任务栏按钮消失 关闭后任务管理器仍有进程，托盘图标仍在
只有托盘右键「退出」才是真正关闭 唯一退出路径 = 托盘菜单「退出」；执行后图标先消失、进程再结束，不留幽灵图标 退出后托盘区无残留图标，进程列表清空
v1.1 追加：左键双击托盘图标 = 显示主窗口 双击图标与菜单「显示主窗口」复用同一回调，效果逐项一致（前台激活、原位置尺寸、最大化状态、任务栏按钮）；单击不做任何事 两种触发方式结果对比无差异
两个必须讲清的取舍：
① 启动即隐藏，用户双击 exe 后"看起来什么都没发生"——这是需求的必然结果。缓解方案见第 10 节（首次启动提示），需要你拍板。
② 窗口的「最小化」按钮不接管（仍最小化到任务栏），只有「关闭」才进托盘。若你希望最小化也进托盘，我加 3 行即可，但会改变现有 Windows 使用习惯，默认不做。

2方案选型：为什么走原生 Win32，而不是 tray_manager

这是本稿最关键的技术决策，直接影响你在"只能远程编译"约束下的返工次数。

维度方案 A · 原生 Win32 runner（推荐）方案 B · tray_manager + window_manager
实现位置新增 windows/runner/tray_icon.cpp/.h，改 3 个 runner 文件改 lib/main.dart、app_root.dart，加 2 个 pub 依赖、加 1 个 ico 资源
新增依赖0 个（只用系统 shell32 / user32）tray_manager、window_manager（含 screen_retriever 传递依赖）
依赖解析风险无。不改 pubspec.lock，flutter pub get 变化为零有。tray_manager 最新 0.8.0 要求 Dart ≥ 3.13，而本项目 sdk: ^3.11.5，很可能解析失败或需回退 0.5.x 老 API
启动时序托盘图标在 C++ 层创建，早于 Dart 引擎首帧，启动即常驻必须等 Flutter 引擎起来、Dart 执行到 main() 才有图标，中间有窗口空窗期
关闭拦截直接吃 WM_CLOSE，语义确定，不受插件版本行为影响依赖 setPreventClose + onWindowClose 回调，链路更长
影响其他平台零影响：只动 windows/ 目录，Android/iOS/macOS/Linux 编译产物完全不变Dart 代码要写 Platform.isWindows 分支，跨平台构建都要重新验证
代码量约 +180 行 C++，Dart 0 行约 +60 行 Dart、+2 依赖、+1 资源
编译失败风险中低（纯 Win32 API，但受 /W4 /WX 严格告警约束，需要谨慎写）中（pub 解析 + 插件 CMake 兼容 + Dart 版本）
结论采用备选（A 若编译受阻再切）
核心判断：你的痛点不是"功能做不出来"，而是"每验证一次都要 push 一次、等 CI 跑一次"。原生方案把变量压到最少 —— 不引入 pub 版本博弈、不引入跨平台回归、托盘图标直接复用 exe 已内嵌的 IDI_APP_ICON（windows/runner/resources/app_icon.ico，resource id 101），连图标资源文件都不用新增。
已核对的两个真实坑（方案 A 必须处理，不处理必编译失败/乱码）：
① windows/CMakeLists.txt 里 APPLY_STANDARD_SETTINGS 用了 /W4 /WX（告警即错误），但没有 /utf-8。源码里写中文 L"显示主窗口" 会触发 C4819 直接编译失败，或在 CI 英文环境下变成乱码菜单 → 必须给 runner 目标补 /utf-8。
② Shell_NotifyIcon 属 shell32，虽然 WIN32 子系统默认链接表通常已含，但在 CMake 里显式补 shell32.lib 才稳。

4窗口状态机：只有一条路能到「退出」

核心是让 主窗口可见 与 进程退出 之间不存在任何直接通路。

图 4-1　窗口状态机（隐藏态是唯一的"归宿态"，退出只能从隐藏态由托盘菜单触发）
为什么关闭时"隐藏"而不是"销毁窗口"：销毁后再重建会丢窗口位置/尺寸/最大化状态，且 Flutter 引擎需要重建渲染表面（有白屏风险）。SW_HIDE 仅隐藏，恢复时是"原样弹出"，也符合"缩小到托盘"的直觉。

6三条关键路径的调用顺序

顺序错了就会出现"幽灵图标"和"关不掉"这两个典型的托盘 bug。

路径 A · 启动（必定隐藏）

  1. wWinMain → FlutterWindow::Create(...) → 原生窗口创建（WS_OVERLAPPEDWINDOW，此时本来就不可见）
  2. OnCreate → 创建 FlutterViewController → SetChildContent(view) 挂载渲染视图
  3. 【改动】删除模板里的 SetNextFrameCallback([&]{ this->Show(); }) —— 这一行就是"启动会弹出窗口"的唯一原因
  4. 【新增】tray_.Create(hwnd, WM_APP+101, icon, L"Foxel") → Shell_NotifyIcon(NIM_ADD) → 托盘图标出现
  5. 【新增】绑定 on_show / on_exit 回调；注册 TaskbarCreated 消息
  6. 进入消息循环 GetMessage：窗口隐藏但消息照常处理，Dart 业务正常运行

路径 B · 关闭主窗口（只隐藏）

  1. 用户点 X / Alt+F4 / 任务栏右键关闭 → 系统发出 WM_CLOSE
  2. FlutterWindow::MessageHandler 在交给 DefWindowProc 之前拦截：if (!quitting_) { ShowWindow(hwnd, SW_HIDE); return 0; }
  3. 窗口隐藏 → 任务栏按钮消失、Alt+Tab 不再列出、进程与引擎继续存活
  4. （没有这一步，DefWindowProc 会销毁窗口 → WM_DESTROY → PostQuitMessage → 进程直接死掉）

路径 C · 托盘菜单「退出」（唯一真退出）

  1. 右键图标 → WM_APP+101（lParam=WM_RBUTTONUP）→ SetForegroundWindow(hwnd)（不置前景，菜单点外面不会消失——经典坑）
  2. CreatePopupMenu → AppendMenuW(1001,"显示主窗口") → AppendMenuW(1002,"退出") → TrackPopupMenuEx(TPM_RETURNCMD|TPM_RIGHTBUTTON)
  3. 用户点「退出」→ 返回 1002 → PostMessage(hwnd, WM_NULL, 0, 0) 清理菜单残留 → 回调 on_exit
  4. 【顺序关键】先 Shell_NotifyIcon(NIM_DELETE) 删图标，再 DestroyWindow
  5. WM_DESTROY → PostQuitMessage(0) → 消息循环退出 → CoUninitialize → 进程结束
  6. （顺序反了：窗口先没了，托盘回调的 HWND 失效，图标残留成"幽灵图标"，鼠标划过才消失）
退出时不做"等待传输完成"的阻塞：直接结束进程。项目的传输队列本身有持久化，下次启动可续传；如果退出要弹确认框"有 2 个任务进行中"，那属于另一个需求，不在本稿范围。

#坑症状对策
01/W4 /WX 无 /utf-8CI 编译直接失败（C4819），或菜单显示乱码runner 目标追加 /utf-8；源文件保存为 UTF-8

10远程编译验证流程（你的唯一编译通道）

按现有 .github/workflows/build.yml 的实际行为设计，注意最后一条避坑。

  1. 我提交改动到功能分支（例如 feat/windows-tray），不动 main
  2. 触发 Build All Platforms：优先用 Actions → Run workflow（workflow_dispatch） 手动跑，或 push 到该分支
  3. 重点看 Windows App job 的 Build Windows 步骤（CMake 编译 runner 在这一步炸或不炸）
  4. 产物：Artifacts → foxel-windows-zip → 解压运行 Foxel.exe，按第 9 节清单点验
  5. 若编译报错：把 CI 日志里第一处 error C.... 贴给我，我精确修一处再推，不做盲改
避坑：build.yml 末尾那个发布 job 会 gh-release 并依赖 github.ref_name 生成下载链接。直接在 main 分支 push 可能误产生一个以分支名命名的 Release。所以验证阶段走独立分支 + workflow_dispatch，确认通过后再合并、再打 tag 正式发版。

11需要你拍板的 4 件事

确认后我按最终口径一次性改完，再走远程编译。

① 实现路线：确认走原生 Win32（方案 A）吗？
推荐 A：零依赖、零 Dart 改动、只影响 Windows。若你更希望"纯 Dart 可维护"，我改走 tray_manager+window_manager，但要接受可能的 Dart SDK 版本博弈与 4 个平台重新验证。
② 最小化按钮要不要也进托盘？
默认不接管（最小化仍留任务栏，只有关闭进托盘）。若希望"最小化=进托盘"，我再加 WM_SYSCOMMAND/SC_MINIMIZE 拦截（+6 行）。
③ 要不要顺带加「单实例」保护？
建议加（+15 行，仍是零依赖）。理由：启动即隐藏后，用户重复双击 exe 看不到任何反馈，容易点出 3 个实例 + 3 个托盘图标，而便携版的 userdata/prefs.json 会被多个进程互相覆盖。加单实例后：第二次启动直接把已有窗口唤到前台。
④ 首次启动要不要给一次"我在托盘"的提示？
推荐加：仅第一次启动（写个布尔标记到 prefs）显示一条系统托盘气泡「Foxel 已在后台运行，右键托盘图标可显示主窗口」。否则用户容易以为程序没启动。需要额外少量原生代码（NIF_INFO 气泡，约 10 行，仍无依赖）。
